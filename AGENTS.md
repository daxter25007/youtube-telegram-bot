# Repository Guidelines

## Структура проекта

Основной код Telegram-бота находится в `app/`. Обработчики и клавиатуры размещайте в `app/bot/`, работу с PostgreSQL — в `app/database/`, интеграции и бизнес-логику — в `app/services/`, общие небольшие функции — в `app/utils/`. Миграции Alembic хранятся в `alembic/versions/`, служебные команды — в `scripts/`, проектные решения — в `docs/superpowers/`. Тесты находятся в `tests/`; интеграционные проверки отделены в `tests/integration/`. Точка входа приложения — `app/main.py`.

## Установка, запуск и проверки

Проект требует Python 3.12. Из корня репозитория используйте:

```bash
python -m venv .venv
pip install -e ".[dev]"
ruff check .
ruff format --check .
pytest -m "not integration"
docker compose config --quiet
docker compose up -d --build
```

Первые две команды создают окружение и устанавливают зависимости. Ruff выполняет статический анализ и проверку форматирования; pytest запускает автономные тесты. Compose проверяет конфигурацию и поднимает бота, PostgreSQL, Cobalt и локальный Telegram Bot API. Миграции вручную применяются командой `docker compose run --rm bot alembic upgrade head`.

## Стиль кода и именование

Соблюдайте настройки `pyproject.toml`: отступ в четыре пробела, максимальная длина строки 100 символов, целевая версия Python 3.12. Используйте `snake_case` для модулей, функций и переменных, `PascalCase` для классов, `UPPER_CASE` для констант. Добавляйте аннотации типов к публичным функциям. Комментарии пишите по-русски и только там, где они объясняют неочевидное решение. Перед отправкой изменений запускайте `ruff check .` и `ruff format --check .`.

## Тестирование

Тесты написаны на pytest с автоматическим режимом `pytest-asyncio`. Именуйте файлы `test_<feature>.py`, а тесты — `test_<behavior>`. Каждое изменение поведения или исправление ошибки должно иметь детерминированный тест без реальных токенов и внешних сервисов. Полный локальный набор запускается командой `pytest`. Интеграционные тесты требуют явного включения: `RUN_INTEGRATION_TESTS=1 pytest -m integration`.

## Коммиты и pull request

История использует Conventional Commits: `feat:`, `fix:`, `docs:` с кратким описанием в повелительном наклонении, например `fix: validate media redirects`. Один коммит должен решать одну задачу. В pull request укажите цель, существенные решения, изменения конфигурации и выполненные проверки; добавьте ссылку на задачу и снимки экрана для изменений интерфейса.

## Безопасность и конфигурация

Не коммитьте `.env`, токены, cookies и реальные учётные данные. Новые параметры добавляйте в `.env.example` и документируйте в `README.md`. Не ослабляйте проверки URL, сетевую изоляцию Compose и ограничения файлов без отдельного обоснования и тестов.
